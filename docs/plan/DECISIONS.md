# Meld Desktop — Decisions

Architecture and scope decisions, newest last. Each entry: context, decision, evidence/tests. Source of truth for task text: `MASTER-PLAN.md`.

## D-001 — Phase 0 reconciliation strategy (branch `reconcile/0.2.0`)
- **Context:** `main` (e7194c2e) and the released `v0.1.8` (5f1aaf53) diverged at d56350a0: 15 hardening commits only on `main`, 62 feature commits only on the release line (plan §5).
- **Decision:** Branch from `v0.1.8`, cherry-pick all 15 `main` commits with `-x` (bc3d65c4 re-applied as `.gitattributes` + `git add --renormalize`), resolve each conflict feature-preserving (D-002…D-005). Because every `main` change is already on the branch, `main` is then merged into the branch with `git merge -s ours origin/main` (no content change, just ancestry), and the PR is merged into `main` with a **merge commit** (never squash) so that `v0.1.8` and every released tag become ancestors of `main` (`git merge-base --is-ancestor v0.1.8 origin/main`).
- **Evidence:** every non-merge commit in `d56350a0..e7194c2e` has a matching `(cherry picked from commit …)` trailer on the branch (or is the renormalize commit 094aa7a3).

## D-002 — Cherry-pick 1/15 `b0315cad` (review fixes) onto v0.1.8
- **Context:** `main` marks `downloading` rows `failed` at startup; v0.1.8 (`840cd1d1`) turns interrupted downloads into resumable `cancelled` rows.
- **Decision:** Keep the startup cleanup but set `state='cancelled'`, `error='download interrupted; retry to resume'`, so the `.part` file stays resumable (PLAY-055) and no row is stuck in `downloading`.
- **Also:** kept v0.1.8's `playRequestIdRef` ("last click wins") and dropped main's duplicate `playSeqRef`, adding main's extra stale check after autoplay queue resolution; kept v0.1.8 lyrics prefetch with real duration (main used `-1`); kept `account_save_session` and `account_refresh_profile` (TR-H1); added `account_avatar` to the moved `AuthSession`/`SessionStatus` structs; adopted `SCHEMA_SQL` const, Fisher–Yates `shuffled()`, `ActiveDownloadGuard`, 5-minute library sync throttle, sleep-timer ref fix and all regression tests.

## D-003 — Cherry-pick 4/15 `58e116aa` (sealed secrets): seal `sp_dc`/`sp_key` instead of deleting them
- **Context:** `main` deletes `spotifySpDc`/`spotifySpKey` at startup, so the Spotify token can never be refreshed without a new login. The master plan (5.2, S5 "Make Spotify reconnect durable") overrides this.
- **Decision:** `SEALED_KEYS` = `cookie`, `spotifyAccessToken`, `spotifySpDc`, `spotifySpKey`; nothing is deleted. Login saves `sp_dc`/`sp_key` sealed (AES-256-GCM, key in Credential Manager). The startup migration seals v0.1.8 plaintext and `VACUUM`s. If secure storage is unavailable, plaintext stays in place until the next start (same as `cookie`). Using the sealed `sp_dc` for automatic token refresh is tracked under Phase 2 (M2.2), not done here.
- **Tests:** `secrets::tests::migration_encrypts_every_plaintext_secret_and_leaves_no_plaintext_in_the_file`, `migration_keeps_the_session_working_when_secure_storage_is_unavailable`.

## D-004 — Cherry-pick 8/15 `9a0b63fd` (IPC surface): which v0.1.8 commands are restored vs retired
- **Restored (registered, have UI callers):** `account_refresh_profile`, `fetch_lyrics_fresh`, `fetch_lyrics_from_provider`, `history_record_playtime`, `library_artist_state`, `library_toggle_artist_bookmarked`, `ytm_browse`, `ytm_browse_continuation`, `ytm_podcast_cache_detail_page`, `ytm_refresh_saved_podcasts`.
- **Retired (code kept, unregistered, `#[allow(dead_code)]`):** `account_save_session` (no UI caller in v0.1.8 or main; it let the webview write an arbitrary Google cookie; login uses `save_account_session_internal` directly), `clear_guest_session` (no UI caller; `account_logout` covers it and now also clears WebView data), `spotify_search_tracks` and `ytm_podcast_episodes` (no UI caller; superseded by matcher/per-channel browsing).
- **Kept registered:** the 9 `library_*`/`ytm_podcast_channels` commands main flagged as unused are in fact called through a variable command name in `App.tsx` (verified by search), so they stay.
- **Evidence:** `grep` of `src/` for each command name on the reconciled branch. A contract test that every registered command has a caller arrives with typed IPC (M1.2).

## D-005 — Cherry-pick 15/15 `0d7814d3` (expired-stream recovery) on top of v0.1.8 session restore
- **Context:** v0.1.8 keyed the audio-source effect on the whole `player` object (any metadata refresh restarted the song); `main` keyed it on `player.item.id` (replaying the same song would not restart). PLAY-035 asks for a unique playback session ID.
- **Decision:** `player` now carries `session` (from `playbackSessionRef`, bumped on every `playItem()`); the effect is keyed on `player.session`. Kept v0.1.8's resume/persistent-session start logic inside the effect. `recoverExpiredStream()` from `main` re-resolves with the same `playlistId` and `audioQuality` as normal playback, refuses to apply if the session changed meanwhile, and only patches `payload` for the same session.
- **Also:** the `setNotice`/auto-skip fallback from `main`'s `onError` is unchanged.
- **Tests:** frontend tests start in Phase 1 (M1.4); PLAY-031/PLAY-035 stay unticked until then.

## D-010 — Releases are not Authenticode-signed until a certificate exists
- **Context:** Plan §7.3 step 4 needs a code-signing certificate (e.g. Azure Trusted Signing, or SignPath's free open-source program). Only the owner can apply/pay for one.
- **Decision:** Publish unsigned NSIS/portable builds and say so in every release note (SmartScreen warning, how to verify with `SHA256SUMS.txt`). Integrity of *updates* is still guaranteed by the Tauri updater signature (minisign key below). When a certificate is available, add `bundle.windows.signCommand` and the signing secrets; no other change is needed.

## D-011 — Updater: Rust-side commands, signed artifacts, portable gets a link
- **Decision:** `tauri-plugin-updater` is used only from Rust (`updates::app_update_check`, `app_update_install`, `app_open_releases_page`), so no updater permission is granted to the WebView. The endpoint is `releases/latest/download/latest.json`; the public key is in `tauri.conf.json`, the private key and password are the Actions secrets `TAURI_SIGNING_PRIVATE_KEY(_PASSWORD)` (a backup copy was handed to the owner). Install happens only on an explicit click, takes a `VACUUM INTO` backup to `backups/pre-update-X.Y.Z.db` (newest 3 kept) and runs the installer in passive mode. Automatic checks run at most once per 24 h, 15 s after start, and only show a notice. This required Tauri 2.12 (crate and `@tauri-apps/*` npm packages updated together).
- **Portable:** self-update (§7.6 swap helper) is not implemented yet; a portable copy (`portable.marker` next to the exe) is told about the update and offered the release page — no fake "install" button.
- **Tests:** `updates::tests::*` (marker detection, backup naming, backup copy + retention), `src/lib/updates.test.ts` (24 h schedule, progress text), `scripts/tests/release.test.mjs` (latest.json shape, notes, tag check, sums, SBOM/notices).

- **Context:** Plan §7.7 portable mode (data next to the exe, DPAPI key file) is Phase 8 work.
- **Decision:** Until then the portable ZIP behaves like 0.1.8's: data in `%APPDATA%\Meld Desktop`, key in Credential Manager. `README-portable.txt` says so. Unlike 0.1.8 the ZIP now includes `icons/taskbar/*.ico`, so taskbar thumbnail buttons work in the portable copy too.

## D-013 — `cargo audit` policy for releases
- **Decision:** The release workflow fails on any RustSec *vulnerability* and on `npm audit --omit=dev` high/critical findings. Informational warnings are reviewed here instead of blocking: `glib 0.18` (unsound iterator; GTK, Linux-only — not in the Windows build), `paste`/`proc-macro-error` (unmaintained, build-time proc macros from Tauri's dependency tree), `chacha20 0.10.1` (yanked; present in `Cargo.lock` but not in the resolved Windows or Linux dependency graph). Re-check on every Tauri upgrade; full `cargo deny` policy arrives with M1.4 (S5-090/R6-075).

## D-014 — Asset-protocol scope must use `$DATA`, not `$APPDATA` (0.2.0 regression)
- **Context:** Owner report on 0.2.0: many songs, especially in Liked Songs, failed with "The native audio element could not read the resolved stream URL". `database_path()` is `%APPDATA%\Meld Desktop`, and the player cache, downloads and artwork sit beside it. In Tauri 2, `$APPDATA` is `%APPDATA%\<identifier>`, so the scope narrowed in Phase 0 (`$APPDATA/Meld Desktop/**`) matched nothing and every cached or downloaded file was blocked.
- **Decision:** Scope entries are `$DATA/Meld Desktop/{downloads,player-cache,artwork}/**`. At start-up the app also calls `allow_directory` on the real directories from `media_directories()`, so a future data-location change (portable mode, §7.7) cannot reintroduce the bug. Guards: Rust `media_directories_sit_next_to_the_database` (also reads `tauri.conf.json`) and `checks.test.mjs`. The frontend also recovers when a cached file is unreadable: it reports the failure, Rust deletes that player-cache row and file (never downloads), and the song is resolved again.

## D-015 — YouTube Music search layout (2026-07)
- **Context:** Live responses no longer contain `musicShelfRenderer`. They now contain a `musicCardShelfRenderer` (top result plus a few items) followed by one `itemSectionRenderer` per result, with no continuation. 0.2.0 fell back to a deep walk that skipped the top-result card.
- **Decision:** `parse_search` reads card, shelf and item sections in page order and dedupes. The card is reshaped into a list item so it shares `parse_responsive_typed`. Fixture: `tests/fixtures/search-2026-07-item-sections.json` (trimmed live response).

## D-016 — Ciphered formats: yt-dlp EJS in QuickJS (PLAY-002)
- **Context:** Reference Meld (InnerTubeX 0.5.2) and yt-dlp both solve the player's signature and `n` transforms. Desktop discarded every ciphered format, so once the direct-URL clients were refused it had nothing left to try.
- **Decision:** Vendor yt-dlp/ejs 0.8.0 (Unlicense; bundles meriyah ISC and astring MIT; SHA-256 pinned by a test) and run it with `rquickjs` 0.14. The interpreter has no I/O bindings, a 768 MiB memory cap, an 8 MiB stack and a 45 s interrupt deadline. The player id comes from `iframe_api`, the preprocessed player is cached in `player-js/` (newest 2 kept) and in memory with per-challenge answers, and it is re-checked every 6 h. If YouTube is unreachable, the newest cached player is used. It is prewarmed 20 s after start-up (PLAY-016). Measured locally: about 9–17 s to preprocess a new player once (release build), then about 1 s per solve. Unsolved `n` counts as a failed client, because throttled streams are unusable.
- **Not done (by design, §0.2):** no PoToken generation and no SABR. Clients that require a GVS PoToken are only used when signed in or as a last resort.

## D-017 — Client order and failure policy
- **Order** (from InnerTubeX's catalog and live probes on 2026-10-02): ANDROID_VR 1.65.10 → VISIONOS 0.1 → ANDROID_VR 1.43.32 → IOS 21.03.3 (direct URLs), then WEB_REMIX (verified end to end: cipher + `n` solved, 206 for the full file), TVHTML5 downgraded, TVHTML5, WEB_EMBEDDED_PLAYER, WEB_CREATOR (signed in only). The TV clients returned "page needs to be reloaded" from the sandbox's datacenter IP; they stay as late fallbacks.
- **Uploads** (`MLPT` context): signed-in clients only, WEB_REMIX first (PLAY-007, partial).
- **Memory:** the client that served a stream is remembered. If the WebView reports a failure, that client is excluded for that video for 5 minutes (PLAY-005, same TTL as Meld). If every client is excluded, the exclusions are ignored rather than refusing to play. Unavailable, members-only and region-blocked are final and stop the cascade.
- **Frontend:** at most 2 recoveries per playback session; streams count as expired 60 s early (PLAY-030, PLAY-032).

## D-018 — Prove a stream serves the whole file before using it (PLAY-005, PLAY-013)
- **Context:** 0.3.0 downloads failed with 403. Live probes on 2026-10-02: ANDROID_VR 1.65.10 URLs answer 206 for ranges inside the first ~800 KB and 403 for anything later (and for `bytes=0-` and plain GETs). VISIONOS 0.1, ANDROID_VR 1.43.32, IOS 21.03.3 and solved WEB_REMIX URLs serve the full file. The audio element only fetched the start before falling back, so playback looked fine while every download failed.
- **Decision:** After resolving, request 1 KiB at `max(len/2, 1 MiB)` (no probe for files ≤ 1 MiB + 1 KiB). Treat 401/403/404/410 as `StreamForbidden`. Exclude that client for the video (5 min) and demote it for every song for 30 min (`ClientHealth`, stable reorder), then continue the cascade. Network errors and other statuses are inconclusive and do not reject the URL. Cost: one small request per fresh resolve.
- **Downloads:** always `Range: bytes={offset}-`. On a refused URL, mark it and re-resolve (max 3 requests); on 416 with a partial file, restart from 0. Error strings never contain the URL (`without_url`).
- **Verified:** the ignored live test now downloads every client's full stream; ANDROID_VR 1.65.10 is rejected by the probe and the other four clients deliver 3,433,755 / 3,433,755 bytes.

## D-019 — Bounded player-cache fills (PLAY-042, PLAY-043)
- **Decision:** `player_cache::CacheJobs` allows at most 2 fills. Starting a fill for a new song cancels every other fill (a skip means the old song is abandoned). Cancelled fills still count until they have closed their socket and file, so rapid skipping applies backpressure: when 2 are still draining, the new song streams without caching. Re-requests for the same song never start a second fill. Fills poll their cancel flag every 250 ms while waiting for data, delete their `.part` on any error, and `RunEvent::Exit` cancels all fills and removes their `.part` files. Removing a cached song cancels its fill.
- **Not done:** a persisted, resumable download queue for explicit downloads (R6-027) and prefetch of the next track (R6-020).

## D-020 — Playback-cache quota and start-up cleanup (PLAY-041, R6-023, R6-026)
- **Quota:** setting `playerCacheLimitMb`, one of 0 (off), 512, 1024, 2048 (default), 5120, 10240, 20480. LRU key is `player_cache.cached_at`, bumped on every cache hit, so no schema change before the Phase 1 migration work (D3). Enforced after each committed fill, when the limit changes and at start-up. Uncommitted data is bounded by the 2 active fills (D-019). A file Windows refuses to delete (open by the player) keeps its row and is retried later.
- **Never evicted:** offline downloads (separate table and folder).
- **Start-up cleanup:** drop cache rows whose file is gone; delete every `.part` and every unreferenced file in `player-cache/`; in `downloads/` delete only `.part` files no unfinished download can resume. Finished download files are never deleted by cleanup, even without a row.
- **UI:** Settings → Storage → Playback cache shows usage, the limit and a clear action (`player_cache_usage`, `player_cache_clear`).

## D-021 — Lint, format and line-ending rules (TR-L9, R6-075)
- **Prettier 3** formats TS/TSX/JS/JSON/CSS/YAML/HTML with `printWidth: 120` (the code was written for wide lines; 80 would double the churn) and LF endings. Markdown is not formatted (prose and plan tables), nor are vendored files, captured test fixtures (`**/fixtures/**/*.json`) or Rust (rustfmt owns it). The one-time reformat is a formatting-only commit listed in `.git-blame-ignore-revs`.
- **ESLint 9 flat config** (`eslint.config.js`): `@eslint/js` recommended + `typescript-eslint` recommended + `react-hooks` (`rules-of-hooks` error, `exhaustive-deps` warn) + `react-refresh` for `src/`; Node globals for scripts and configs. Unused variables are errors except `_`-prefixed.
- **Warning ratchet:** `npm run lint` uses `--max-warnings 14`, the count at adoption (13 `exhaustive-deps` in `App.tsx`, 1 `only-export-components` in `UpdatePanel.tsx`). New warnings fail CI. Each fix lowers the number (8 after U4-002, D-026); the App.tsx split (U4-001…) should bring it to 0. The hook warnings were not "fixed" blindly, because adding the missing dependencies changes when effects run.
- **Line endings:** `* text=auto eol=lf`, `*.ps1 text eol=crlf` (Windows PowerShell 5.1 reads LF scripts but CRLF is the safe default for signed or edited-on-Windows scripts). `npm run check:tooling` fails if a committed file has CRLF or mixed endings, or if the lint/format scripts or CI steps go missing.

## D-022 — Required status checks on `main` (R6-075, TR-H9)
- **Checks:** `Lint and format` (ubuntu: `check:*` invariants, ESLint, Prettier, `cargo fmt`), `Dependency audit` (ubuntu: `npm audit --omit=dev --audit-level=high`, `cargo audit` with the D-013 policy), `Windows build and tests` (script tests, Vitest, `tsc`, Vite build, clippy `-D warnings`, `cargo test --locked`, `tauri build --no-bundle`) and `Release dry run`. All must come from GitHub Actions (app id 15368), branches must be up to date (`strict`), and **admins are included** (`enforce_admins`), so the owner's token cannot merge red PRs either. Force pushes and deletion of `main` stay blocked. No review requirement while there is one maintainer (S5-097).
- **Why three CI jobs instead of one per tool:** each Windows job costs a full Rust build (about 15 min). Lint/format and audits need no build, so they run on Linux in parallel and fail fast; everything that compiles stays in the one Windows job.
- **Release dry run on every PR:** a path-filtered workflow never reports on unrelated PRs, and a required check that never reports blocks the merge forever. `release.yml` therefore runs on every PR: a `changes` job lists the PR's files (`RELEASE_PIPELINE_PATHS` in `scripts/lib/release.mjs`); the build and Windows smoke run only when the pipeline is touched; the always-reported `Release dry run` job passes when they succeeded or were not needed, and fails if they were needed and did not succeed.
- **Source of truth:** `scripts/lib/branch-protection.mjs`. `GH_TOKEN=… node scripts/branch-protection.mjs` reports drift; `--apply` sets it. A script test fails if a required check is renamed, made conditional, or put behind a path filter.

## D-023 — The downloads row is the resume manifest (PLAY-055)
- **Context:** Downloads resumed from the `.part` file with `Range: bytes=<length>-` and appended to it whenever the server answered 206. After a quality change, or when another YouTube client returned a different file, the bytes of two streams could be joined into one corrupt file.
- **Decision:** No separate manifest file (start-up cleanup and the downloads folder stay as they are). The `downloads` row already names the partial (`path`) and records the announced full size (`total_bytes`); a retry now keeps `total_bytes` while a partial exists. A resumed response is appended only when it is 206 and its `Content-Range` starts exactly at the partial length and announces the same total. A different or missing total, a range that starts elsewhere, or 416 deletes the partial and requests from byte 0; a 200 (range ignored) rewrites the file from its body. Rows without a recorded size are not trusted and restart.
- **Code:** `src-tauri/src/download_resume.rs` (`resume_decision`, `parse_content_range`, `write_body`, `next_chunk_within`). Tests run real transfers against a local HTTP server that honours ranges: cancel, then resume after a simulated app restart; a partial from another stream; a partial that is already complete.

## D-024 — `main` is the canonical branch (QUEUE-001)
- **Decision:** `main` is the single source of every release (enforced by `release.yml`), and queue/playback/download behaviour has one implementation with tests on `main`. The rule is written down in `CONTRIBUTING.md`.
- **Queue logic extracted:** `src/lib/queue.ts` (shuffle arrangement, shuffle-after-current, remove, move, continuation append), `src/lib/playbackSession.ts` (occurrence keys, refresh, resume position), `src/lib/persistentPlayback.ts` (restore after restart) and `src/lib/audioQuality.ts` are pure modules used by `App.tsx` and covered by Vitest. Behaviour is unchanged except that a continuation page listing the same new song twice now appends it once.
- **Old remote branches (2026-10-02):** every desktop branch used for 0.2.0–0.3.0 is merged. Not merged: `development`, `feature/remote-gql-hash-sync`, `fix/android-auto-spotify-playlists`, `fix/issue-cleanup-batch`, `fix/liked-order-and-stop-on-task-clear` (Android app history, not desktop code), `gh-pages` (site), and `feat/source-parity-next` (one desktop commit `a0227856`, 2026-08-31: treat a like response without `feedbackResponses` as success unless it has an `error`, and find account avatars in more response shapes). That commit is not on `main`; porting it is a separate change with tests (owner to confirm it is still wanted). No branch was deleted.

## D-025 — How `App.tsx` was split into screens (U4-001)
- **Decision:** Every route-level screen and overlay is its own component under `src/features/<area>/` (Home, Search, History, Stats, Library, Playlist, Detail, Settings, Spotify playlist/liked, Lyrics panel, Queue panel, Player bar, Expanded player). Shared types live in `src/types.ts`, helpers in `src/lib/`, small shared components in `src/components/`. The JSX was moved mechanically (TypeScript language service), so markup and behaviour are unchanged; each component receives what it uses as typed props.
- **Still in `App.tsx` on purpose:** state, effects and handlers. Moving them is U4-002 (feature modules) and U4-008 (state ownership); doing it in the same change would have mixed a pure move with behaviour changes. Album, artist and podcast pages share `DetailScreen` until the typed router (U4-003) gives them their own routes. Overlays keep their open condition inside the component.
- **Guard:** `scripts/lib/ui-structure.mjs` (`ROUTE_SCREENS`, `checkScreenSplit`) makes `npm run check:ui` fail if a route's screen component disappears or its markup is inlined back into `App.tsx`. The UI invariant checks now read all of `src/`, not just `App.tsx`.

## D-026 — Feature state boundaries as hooks (U4-002)
- **Decision:** Each feature in U4-002's list owns its state in one hook under `src/features/<area>/`: `useNotice` (notifications), `useSelection`, `useSettingsState`, `useAccounts` (Google/Spotify status, sign-in events, connect/logout), `useDownloads` (download commands, their notices, progress of the open menu's item), `useItemMenu` (item menu and its dialogs), `usePlaylists`, `useSpotifyLibrary`, `useLyrics` + `useLyricsFollow`, `useQueue`, `usePlayer`, `useSleepTimer`. A hook takes the few values it needs from other features as explicit parameters (for example `useQueue({ settings, setNotice })`), so the dependency direction is visible.
- **`App.tsx` is the composition root:** it calls the hooks in dependency order and still holds the cross-feature actions (`playItem`, `performMenuAction`, navigation, `goBack`) and the per-screen data (home, search, library, history, detail). Those move with the typed router (U4-003) and server-state separation (U4-008).
- **Behaviour:** state moved verbatim with a TypeScript language-service codemod. Deliberate changes: start-up loads, the Settings refresh and the global keyboard shortcuts use `useEffectEvent` (React 19.2), so the keydown listener is attached once instead of after every state change; `hideItem`, `matchesPlaylistQuery` and `seekPlayback` are memoised. The lint warning ratchet drops from 14 to 8.
- **Guard and tests:** `checkFeatureModules` (`FEATURE_MODULES` in `scripts/lib/ui-structure.mjs`, run by `npm run check:ui`) fails if a hook disappears, App stops using it, or App re-declares state the hook owns. `src/features/featureModules.test.tsx` tests the hooks with React Testing Library in jsdom (dev dependencies `jsdom`, `@testing-library/react`). `src/App.test.tsx` mounts the whole app with mocked Tauri APIs, which catches hook-ordering mistakes the compiler cannot see.

## D-027 — Typed routes and route-based history (U4-003, U4-004)
- **Routes:** `src/app/routes.ts` defines `Route`, a union with one member per durable surface: home, search (query), library (mode), history (source), stats (period), album/artist/podcast (browse ID), browse (browse ID + optional params), playlist (YouTube Music or `LOCAL_<n>` ID), Spotify playlist, Spotify liked songs and settings (page). `routePath`/`parseRoutePath` serialise them as app paths (`/album/MPREb_x`, `/search?q=…`); parsing validates every parameter (IDs `[A-Za-z0-9_-]{1,200}`, enums, query ≤ 500 characters) and returns null for anything else, so a stored or linked route can never carry arbitrary input into a command.
- **Derived, not duplicated:** the visible route is computed from view state by `routeFromView` (topmost surface first). App keeps its state; the route is a read model plus `showRoute`, which turns a route back into view state. `<main data-route>` exposes it for tests.
- **History:** `src/app/history.ts` replaces the two `NavKey[]` stacks with entries `{ route, tab, scrollTop }` (`pushEntry`, `stepBack`, `stepForward`, at most 50 entries, repeated routes collapse). Back/forward re-open the route, including a detail page or playlist that was open when the user left, re-select the sidebar tab it was opened from, and restore the scroll offset once the page is tall enough. `goBack` still closes open layers first (U4-005 makes that order explicit).
- **Limits:** a browse page derived from the view has no `params` (the loaded page does not carry them), so returning to a mood/genre browse page reloads its default view. Filters and search results are refetched, not cached (U4-010).

## D-028 — One stacking order for overlays (U4-005)
- **Context:** Back and Escape each had their own hard-coded priority list, and they disagreed (Escape closed Settings before the logout dialog opened from it; Back ignored dialogs and the Spotify screens; Escape closed every panel at once).
- **Decision:** `src/app/layers.ts` lists every overlay once, topmost first: dialogs, the item menu, the Settings page, player panels (lyrics, queue, expanded player), then nested screens (playlist, detail, Spotify playlist, Spotify liked). App derives `layerState` from its state; Back and Escape both close `topmostLayer(layerState)`, one layer per press. Only when nothing is open does Back step through the route history (D-027); Escape then does nothing. The Back button is enabled whenever a layer is open or history exists.
- **Not a route:** overlays stay view state, not history entries. Dialogs and menus are short-lived, and restoring them after a restart would be wrong for confirmations and sign-in (U4-006).

## D-029 — Restoring the last page (U4-006)
- **Decision:** App stores the page route and its sidebar tab in `localStorage["meld:lastRoute"]` whenever the page changes (`src/app/lastRoute.ts`) and shows it again at start-up through the same `showRoute` used by back/forward. Home stores nothing.
- **Never restored:** Settings (a modal whose Integrations page starts sign-ins), every dialog and confirmation (they are not routes, D-028), and a search for a link: re-running it would open the item, and for a video start playback by itself; it comes back as an empty search page. Spotify pages fall back to the library because the Spotify session is only known after start-up.
- **Validation:** the stored value goes through `parseRoutePath` and a tab allow-list; anything malformed is ignored. Back/forward to a link search also shows the link without opening it; only a typed search opens links.

## D-030 — One link parser (U4-007)
- **Decision:** `src/app/links.ts` `parseLink` is the only place that reads pasted links. It returns a page route (`meld:` URIs, app paths such as `/album/MPREb_…`, YouTube Music browse/playlist/channel URLs, Spotify playlist URLs and `spotify:playlist:` URIs), a video (YouTube, YouTube Music and youtu.be watch/shorts links) or a Spotify track/album/artist reference. Hosts and IDs are checked strictly; anything else is an ordinary search. `src/lib/urls.ts` is removed; the item menu and last-page restore use `parseLink` too.
- **Fixes:** `music.youtube.com/playlist?list=…` used to open a bogus `MPREb_<list>` album; it now opens the playlist. `/browse/MPREb_…` used to be treated as an artist; it now opens the album.
- **Navigation:** a typed page link opens the page straight away without a search page in between, so Back returns to the page the link was pasted on. Video and Spotify track/album/artist links still show the search page (playback starts, or a notice says to search by name, because Meld has no direct Spotify catalogue pages).
- **Not here:** registering `meld://` with the operating system is S5-075.

## D-031 — Server state in a keyed resource cache with request identities (U4-008, U4-009)
- **Context:** App.tsx held every fetched page (home, search, library, history, stats, detail, playlist) in `useState` next to dialog booleans and player controls, and every loader wrote its answer into that one slot whenever it arrived. Opening album B while album A was loading showed A when its answer came in late; the same happened to searches and library filters.
- **Decision:** `src/data/resourceCache.ts` (`ResourceCache`) holds server state as entries keyed by what was fetched (`src/data/keys.ts`: `home`, `search:<query>`, `library:<mode>`, `library:podcasts:<filter>`, `library:top:<period>`, `history:<source>`, `stats:<period>`, `detail:<kind>:<id>:<params>`, `playlist:<id>`). Six data hooks own the fetching: `useHomeData`, `useSearchData`, `useLibraryData`, `useHistoryData` (history + stats), `useDetailData`, `usePlaylistData`. React reads entries with `useSyncExternalStore` (`src/data/useResource.ts`). App keeps only view state: which tab, mode, query and period are shown, and which detail page (`detailRef`) or playlist (`openPlaylist`) is open. The visible route is derived from that view state, not from loaded data.
- **Request identity (U4-009):** every load gets an id; only the newest load of a key commits. Loads carry a scope per screen (`detail`, `playlist`, `search`, `library`, `history`, `stats`); starting one aborts the older load of that scope, whose entry goes back to its last good state (or is removed), so no spinner is left behind. Continuations ("load more") take a token from `begin()` and are merged into the key they were requested for, never into whatever page is open now. Tauri commands cannot be interrupted yet, so the `AbortSignal` only drops the answer; real backend cancellation is S5-009.
- **Caching:** at most 60 entries, least recently written first out (in-flight entries are never evicted). Back/forward reuse an entry fetched in the last 10 minutes (`FRESH_FOR_MS`) as it was left; a typed search, a sidebar click and explicit refreshes always fetch again. Mutations keep refetching the affected page as before (`reloadPlaylist` after removing a song).
- **Not used:** a query library (TanStack Query, SWR) or zustand. The cache is ~200 lines, has no dependencies and is tested directly; it can be swapped later without touching the screens because they only see `LoadState` values.
- **Guard:** `checkServerState` (`scripts/lib/ui-structure.mjs`, run by `npm run check:ui`) fails if a data hook disappears, App.tsx calls one of the page commands itself, or App.tsx keeps a page in `useState` again. Queue continuations are player state and stay with the queue until the playback coordinator (M4.1).

## D-032 — Screen state travels with the history entry (U4-010)
- **Decision:** a history entry (D-027) also stores the screen's view state when it was left: `src/app/screenState.ts` `captureScreenState(route, …)` keeps the Library search, sorts, grid/list layout, podcast filter, top-songs period and playlist-list filters for library routes, the History search for history routes, and the query and sort for Spotify playlist/liked routes. Back/forward apply it in the same update as the route (`applyScreenState`), so the screen loads once, with the filters it was left with. A snapshot is applied only to the kind of screen it was taken from (`screenStateMatches`).
- **Routes are their own state:** search (the query is in the route, the results come from the cache, D-031), album/artist/podcast/browse and playlist pages store nothing extra.
- **Scroll:** an open album, artist, podcast, playlist or Spotify screen scrolls inside its panel (marked `data-screen-scroll`), so the entry records and restores that panel's offset instead of the page's. The offset is applied once the page is tall enough (D-027).
- **Not persisted:** screen state lives only in the in-memory history. The last-page restore after a restart (D-029) still restores the route only.

## D-033 — One capability model for item menus (U4-011)
- **Context:** the item and player menus were ~200 lines of JSX in App.tsx, each button behind its own condition (item kind, `videoId`/`localPath`, Google or Spotify sign-in, library/download state, which screen was open). The same rules were not checked when the action ran.
- **Decision:** `src/app/capabilities.ts` `itemMenuEntries(item, context)` returns the menu, in display order, from the item (kind, YouTube or local source), a `MenuContext` (surface `item`/`player`, Google and Spotify sign-in, local-list context, open playlist, playback-cache list, `LibraryItemState`, download state, Spotify match) and nothing else. `src/features/menu/ItemMenu.tsx` only renders the entries (quick entries share a button row, notes show download status). `performMenuAction` first checks `canPerform(action, item, context)`, so a menu that went stale (signed out, download finished) cannot run an action it no longer offers; it closes and says so.
- **Behaviour:** the entries, labels and order are the same as before. Player-only entries (Advanced playback, Sleep timer, Copy playback report) and Spotify's Add to playlist are `MenuAction`s too, dispatched by `runMenuAction`.
- **Guard and tests:** `checkCapabilities` (`npm run check:ui`) fails if App.tsx stops rendering `<ItemMenu>`, stops calling `canPerform`, or calls `performMenuAction` with a literal action again. `capabilities.test.ts` covers type, source, account, state and surface rules; `App.test.tsx` opens a real menu.
- **Later:** selection-bar actions, the player bar's like button and Spotify track menus still have their own conditions; they move to this model when those surfaces are reworked (M5/M6).

## D-034 — One notification center (U4-013)
- **Context:** feedback was one `notice` string that the next message overwrote. Errors vanished after a few seconds like any other message, a long job could not show progress, and nothing offered an action (Undo, Retry).
- **Decision:** `src/app/notifications.ts` holds the model as pure functions: a notification has a kind (`info`, `success`, `warning`, `error`, `progress`), an optional `key` (a later one with the same key replaces it in place: progress updates, a retry), an optional action and progress. Errors and progress stay until dismissed or replaced; the rest time out (info 6 s, success 5 s, warning 10 s). A repeated message is counted (×2) instead of stacking; at most 4 are shown and the oldest transient one goes first. `useNotice` keeps the list; `NoticeStack` renders it (errors with `role="alert"`, the rest as a polite status).
- **Compatibility:** `SetNotice` is `(message | NoticeInput, kind?)`, so `setNotice("…")` still works as info and `setNotice("")` clears only transient notifications. Existing messages were tagged with a kind (about 70 errors, 27 warnings, 18 successes). Library sync and Spotify playlist downloads report progress under one key and end in success or an error with Retry.
- **Tests:** `notifications.test.ts` (kinds, timeouts, key replacement, counting, limit, clearing); `App.test.tsx` (an error stays with Retry, then success replaces it).

## D-035 — One destructive-action policy (U4-012)
- **Context:** removals decided on their own whether to ask (`window.confirm` in one place, nothing elsewhere), whether to update the screen first, and what to do on failure. None offered Undo.
- **Decision:** every removal is a `DestructiveSpec` run by `runDestructive` (`src/app/destructive.ts`) and is classed by severity:
  - `permanent` (cannot be taken back: delete an uploaded song, remove from YouTube Music history, remove a download file, clear Meld or search history, remove a YouTube Music playlist song, remove a Spotify playlist track) → asks first in `ConfirmDialog` (an `alertdialog`, Cancel focused, topmost `confirm` layer so Escape and Back close it first);
  - `undoable` (an exact reverse exists: unlike, unpin, remove from library, unsubscribe a podcast or artist, unsave an episode, remove a song from a local playlist) → no question, a success notification with Undo for 10 s;
  - `disposable` (only cache Meld rebuilds on demand: a cached song, the playback cache) → neither.
  An optional `optimistic()` changes the screen first and returns its rollback, used when the commit fails; the failure is an error notification whose Retry runs again without asking. `refresh` runs after the commit and after an undo.
- **Notes:** undoing a local playlist removal adds the song back at the end, not at its old position (there is no insert-at command yet). The sign-out dialog keeps its own flow; it is not a removal.
- **Guard and tests:** `checkDestructivePolicy` (`npm run check:ui`) fails on `window.confirm`, when App.tsx stops rendering `<ConfirmDialog>` or `<NoticeStack>`, or when a removal branch of `performMenuAction` or `useDownloads` no longer calls `destructive(...)`. `destructive.test.ts` covers cancel, rollback + Retry without a second question, Undo and disposable actions; `App.test.tsx` clears local history through the dialog.

## D-036 — Error boundaries per region (U4-014)
- **Context:** one render error anywhere (a malformed album answer, a bad lyric line) unmounted the whole React tree: a blank window, and the `<audio>` element inside the player bar went with it, so the song stopped.
- **Decision:** `src/components/ErrorBoundary.tsx` wraps each region: the routed page (reset when the route changes), the album/artist page, the playlist page, both Spotify pages, Settings, the queue, the full player, the lyrics panel (each reset when it closes or another item opens, with a Close button), and the player controls (reset per playback session). The fallback names the region, shows the error and offers Try again. Errors are logged to the console and kept in `renderErrors` (`src/app/renderErrors.ts`, last 20).
- **Playback:** the `<audio>` element and its event handlers moved from `PlayerBar` into `PlayerAudio`, rendered before the controls' boundary, so a failing control strip, panel or page never stops the song.
- **Guard and tests:** `checkErrorBoundaries` (`npm run check:ui`) fails if the page or an overlay loses its boundary or `<audio>` returns to PlayerBar. `ErrorBoundary.test.tsx` (fallback, Close, Try again, reset key); `App.test.tsx` (a broken album page leaves the shell usable).
